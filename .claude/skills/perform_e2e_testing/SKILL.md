# Skill: End-to-End Scenario Testing

## Workflow (작업 순서)

1. **E2E 스택 확인 (Stack Binding)**
   - `Read`로 `.claude/_workspace/01_architecture/design.md`의 「기술 스택」·「소유권」·「표준 명령어」에서 E2E 프레임워크, 테스트 경로, 빌드·실행·E2E 명령을 확인한다.
   - 🚨 **주의:** E2E 도구를 스스로 가정하지 않는다. 명시가 없으면 작성을 멈추고 호출자에게 질의한다.

2. **시나리오 및 DoD 분석 (Scenario Review)**
   - `.claude/_workspace/02_issues/` 하위의 완료된 이슈 명세서와 기획서(`design.md`)를 분석한다.
   - 🚨 **주의:** 내부 구현 코드를 훔쳐보고 테스트를 맞추려 하지 말고, 오직 '사용자의 관찰 가능한 행동과 결과' 관점에서만 시나리오를 기획한다.

3. **E2E 테스트 스크립트 작성 (Test Implementation)**
   - 소유권 표의 E2E 테스트 경로에 확정된 프레임워크 문법으로 테스트 코드를 작성한다.
   - 단순 응답 코드가 아니라, 화면에 보이는 텍스트·상태 변화·이동 결과 등 **사용자에게 드러나는 변화(Assertion)**를 깐깐하게 검증하도록 짠다.

4. **실행 환경 구성 및 구동 (Build & Run)**
   - `Bash` 도구로 `design.md`의 표준 빌드 명령을 실행해 애플리케이션을 프로덕션에 준하는 모드로 준비한다.
   - 표준 실행 명령으로 애플리케이션을 띄우고(또는 E2E 프레임워크의 서버 자동 기동 설정을 활용), 표준 E2E 명령을 실행한다.

5. **결과 판독 및 피드백 (Validation & Routing)**
   - **실패(Red) 시:** 에러 지점의 로그와 화면 증거를 수집하여, `SendMessage`로 프론트엔드/백엔드 개발자에게 재현 절차와 원인을 통보하고 즉시 작업을 멈춘다. 절대 프로덕션 코드를 스스로 고치지 않는다.
   - **성공(Green) 시:** 모든 시나리오가 통과하면 `[E2E TEST PASSED]`를 출력하고, 마스터 오케스트레이터에게 통제권을 넘겨 커밋을 진행하도록 유도한다.

## Why (왜 이렇게 하는가?)

- **진짜 유저 경험(UX) 검증:** 단위 테스트가 모두 통과했더라도, 실제 실행 환경에서는 레이아웃이 겹치거나 통신 정책(CORS 등)이 막힐 수 있다. 이를 릴리즈 직전에 완벽히 차단하기 위함이다.
- **책임의 분리 (Separation of Concerns):** 테스터가 코드를 직접 고치게 두면 원칙이 무너진다. E2E 테스터는 오직 '발견'만 하고, 수정은 철저하게 구현 담당(FE/BE)이 책임지도록 강제하기 위함이다.
