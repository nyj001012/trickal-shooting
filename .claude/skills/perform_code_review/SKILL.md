# Skill: Enterprise-level Code Review & Security Audit

## Workflow (작업 순서)

1. **검수 기준 확정 (Rulebook Binding)**
   - `Read`로 `.claude/_workspace/01_architecture/design.md`의 「기술 스택」·「디렉터리 구조 및 소유권」·「표준 명령어」·「아키텍처 규약」을 읽어 이번 프로젝트의 검수 기준을 확정한다.
   - 🚨 **주의:** 리뷰 기준은 리뷰어의 취향이나 익숙한 프레임워크가 아니라 이 문서다. 규약에 없는 지적은 **반려가 아니라 '규약 공백' 제안**으로 분류한다.

2. **계약 준수 여부 검증 (Contract Verification)**
   - `.claude/_workspace/03_contracts/`의 계약과 실제 구현의 시그니처·스키마가 100% 일치하는지 대조한다.
   - 파라미터 누락, 만능 타입(`any`·자유 형식 딕셔너리) 사용, 합의되지 않은 응답 포맷 변경이 있는지 확인한다.

3. **정적 분석 및 테스트 통과 확인 (Static Analysis & Tests)**
   - `Bash` 도구로 `design.md`의 표준 명령어(린트, 정적 타입 검사, 테스트)를 실행한다.
   - 단 하나의 경고(Warning)나 실패(Red)라도 존재할 경우 즉시 리뷰를 중단하고 반려(Reject)한다.

4. **백엔드(BE) 아키텍처 및 성능 검수 (Backend Audit)**
   - **트랜잭션:** 다중 쓰기가 규약이 정한 계층(일반적으로 비즈니스 로직 계층)에서 하나의 트랜잭션으로 묶였는지, 데이터 접근 계층이 트랜잭션을 열지 않았는지 검사한다.
   - **로깅:** 로거를 인자로 넘기는 드릴링이 발생했는지 확인하고, 규약이 정한 요청 컨텍스트 기반 구조화 로깅을 사용했는지 검수한다.
   - **성능:** 반복 쿼리(N+1), 불필요한 전체 조회, 요청 처리를 막는 동기 블로킹 코드가 없는지 확인한다.

5. **프론트엔드(FE) 렌더링 및 메모리 검수 (Frontend Audit)**
   - **리소스 누수:** 실시간 연결·타이머·이벤트 리스너·스트림에 대한 해제(cleanup) 처리가 완벽한지 검수한다.
   - **렌더링 경계:** 규약이 정한 서버/클라이언트 렌더링 분리와 상태 소유 위치를 지켰는지 확인한다.
   - **에러 및 로깅:** 오류 격리와 폴백 UI가 적용되었는지, 개별 요소에 하드코딩된 로깅 대신 공통 이벤트 수집 계층을 사용했는지 확인한다.

6. **소유권 경계 검수 (Ownership Audit)**
   - 각 구현 에이전트가 소유권 표 밖의 경로(특히 테스트 코드와 계약 파일)를 수정했는지 대조하고, 위반 시 즉시 반려한다.

7. **구체적 피드백 반환 (Concrete Feedback & Approve)**
   - "코드를 최적화하세요" 같은 추상적인 지적을 금지한다. 반드시 **잘못된 코드 라인과 확정 스택 관용에 맞는 대안 코드 스니펫(Snippet)**을 포함하여 `SendMessage`로 반려 사유를 해당 구현 에이전트에게 전송한다.
   - 모든 검수를 통과했을 경우 "Approve 완료" 메시지를 전송하고 다음 단계 진행을 승인한다.

## Why (왜 이렇게 하는가?)

- **기술 부채 원천 차단 (Prevent Technical Debt):** 타협해서 통과시킨 나쁜 코드는 운영 환경에서 병목과 장애로 돌아온다. 리뷰어는 개발 속도보다 시스템의 안정성을 무조건 최우선으로 삼는 게이트키퍼여야 한다.
- **취향 논쟁 차단 (Objective Rulebook):** 기준을 설계 산출물에 고정하면, 스택마다 달라지는 리뷰어의 선호로 인해 구현 에이전트가 흔들리는 일을 막을 수 있다.
- **핑퐁 횟수 최소화 (Reduce Context Switching):** 모호한 피드백은 불필요한 재시도를 낳아 토큰을 낭비한다. 한 번 반려할 때 명확한 코드 대안을 제시하여 피드백 루프를 최단기로 끝내기 위함이다.
